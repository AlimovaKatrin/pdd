# Правила работы над PDD

Эти инструкции действуют для всего репозитория. Прочитай их до изменения кода.

## Версия игры и документов

Номер версии имеет вид `0.3.0-preview.1`: три числа и, для предварительного выпуска, пометка `preview` с номером.

- **Первое число — основной этап продукта.** `0` означает раннюю разработку. `1.0.0` — первый стабильный выпуск с выполненными требованиями и проверками. После него первое число повышается при крупных несовместимых изменениях, которые требуют перехода пользователей или их данных на новый формат.
- **Второе число — новый набор возможностей.** Например, переход с `0.2.0` на `0.3.0` обозначает добавление других машин, увеличенной карты и правил проезда перекрёстков. При его повышении третье число сбрасывается в `0`.
- **Третье число — исправления выпущенной версии.** Например, `0.3.1` исправляет ошибки `0.3.0`, не добавляя новый набор возможностей.
- **`preview.N` — предварительный выпуск.** Первая проверяемая сборка нового набора возможностей получает `preview.1`, следующая — `preview.2`. Номер повышается для нового предварительного выпуска, а не после каждой правки или локального запуска. Для нового набора возможностей счёт начинается с `1`.
- Пометка `preview` снимается после выполнения требований и приёмки этой версии: `0.3.0-preview.2` → `0.3.0`. Это означает готовность заявленного набора возможностей, а не поддержку всех ПДД.
- **Версия ТЗ совпадает с версией игры, которую оно описывает.** Не вводи отдельную нумерацию ТЗ вроде `1.3`. Уточнение текста не повышает версию игры; обновляй дату документа. План будущей версии помечай как план, не называй её уже выпущенной.
- При выпуске согласованно обновляй версию в `package.json`, сведениях о проекте в `package-lock.json`, документации и тех местах интерфейса, где она показана. Различай текущую и планируемую версии. Само обсуждение следующей версии не является выпуском и не меняет текущий номер.

Пример последовательности: `0.3.0-preview.1` → `0.3.0-preview.2` → `0.3.0` → `0.3.1`. Это правило нумерации проекта, а не календарный план выпусков.

## Простой язык во всех описаниях

- Пиши простым, понятным русским языком во всех текстах проекта: ТЗ, планах, документации, описаниях версий, интерфейсе, разборах нарушений и сообщениях о результатах работы.
- Начинай с главного: что происходит, зачем это нужно и что получит игрок или разработчик. Описывай конкретные действия и результаты.
- Используй короткие предложения и небольшие абзацы. Один абзац — одна мысль. Убирай повторы, канцелярские обороты и детали, которые не помогают понять задачу.
- Заголовки должны помогать найти ответ. Списки используй для шагов и перечислений, таблицы — для сравнения. Не перегружай текст кодами требований, большими таблицами и повторяющимися оговорками.
- Объясняй непривычные термины при первом использовании. Технические подробности оставляй в технических документах; в ТЗ описывай поведение игры и ожидаемый результат.
- Если правило трудно понять, добавь короткий пример из поездки. Отделяй предложение от принятого решения, запланированное — от сделанного, а проверенное — от предположения.
- Упрощай объяснение ПДД, сохраняя его смысл и важные условия. Дословные нормативные цитаты не переписывай и не смешивай с авторским пояснением.
- Перед завершением перечитай текст: понятен ли он человеку без истории чата, можно ли быстро найти главное и ясно ли, что уже работает и что осталось сделать?

## Чистый и понятный код

- Пиши простой, читаемый код, который другой разработчик может понять без устного объяснения. При выборе решения оценивай ясность логики и лёгкость изменений, а не минимальное количество строк.
- Давай переменным, функциям и типам имена по их смыслу в задаче. Избегай неочевидных сокращений; называй сложные условия и числовые пороги, указывай единицы измерения там, где они важны.
- У каждой функции, компонента и модуля должна быть понятная ответственность. Разделяй независимые задачи и этапы обработки; не накапливай управление состоянием, расчёты, сохранение и отображение в одном большом файле.
- Выстраивай логику последовательно: входные данные, проверки, основные действия, результат. Уменьшай вложенность ранними выходами; избегай вложенных тернарных операторов, скрытых побочных эффектов и плотных цепочек выражений.
- Выделяй функции и модули, когда это даёт самостоятельный понятный смысл или устраняет повторение одного правила. Не дроби код ради количества файлов и не создавай обёртки, которые лишь заставляют переходить между файлами.
- Строй чистую архитектуру в рамках слоёв, описанных ниже: бизнес-правила отделяй от интерфейса и инфраструктуры, зависимости направляй внутрь, состояние и побочные эффекты закрепляй за явным владельцем.
- Выбирай самое простое решение, достаточное для текущих требований. Новые слои, интерфейсы и универсальные механизмы вводи только для конкретной задачи; не проектируй расширения на гипотетическое будущее.
- Комментариями объясняй причины решений, ограничения и неочевидные правила. Очевидные действия должны читаться из имён и структуры кода; комментарии не заменяют упрощение логики.
- Соблюдай пустые строки и остальные правила `docs/STYLEGUIDE.md`, чтобы импорты, объявления и логические блоки были визуально разделены.
- При рефакторинге сохраняй поведение, если задача не требует его изменения, и подтверждай это подходящими тестами. Перед завершением перечитай изменённый код: можно ли понять основной сценарий и переходы состояния без восстановления скрытых связей?

## Архитектура и зависимости

Один клиентский проект с разделением ответственности. Не вводи микросервисы, универсальный игровой движок, ECS или сложный DI-контейнер без конкретной необходимости.

Целевая структура; создавай каталоги по мере появления кода:

```text
src/
  domain/
    entities/     # участники и их состояния
    world/        # постоянная карта, изменяемый мир, связи объектов
    simulation/   # расчёт следующего состояния мира
    maneuvers/    # начало, ход и завершение манёвров
    rules/        # выбор применимых проверок и обнаружение нарушений
    violations/   # нарушения и подтверждающие обстоятельства
    learning/     # соответствие и выбор вопроса, оценка ответа
  use-cases/
    ports/        # интерфейсы хранения и получения материалов
    session/      # владелец мира и состояния поездки
                  # start-trip, step-simulation, handle-violation,
                  # pause/resume-trip, answer-question, retry-situation,
                  # return-to-road, finish-trip, clear-history
  adapters/
    input/        # клавиатура → команды игры
    runtime/      # игровой цикл, фокус окна
    persistence/  # IndexedDB
    content/      # локальные данные через LearningContentProvider
  presentation/
    react/        # меню, HUD, карточки, журнал, настройки
    phaser/       # город, участники, камера, анимации
    view-models/  # подготовленные данные для интерфейса
  content/
    maps/
    questions/
    explanations/
    rule-references/
  bootstrap/      # создание и связывание модулей, освобождение ресурсов
public/assets/    # статические ресурсы
tests/
  unit/           # отдельные правила и функции
  integration/    # взаимодействие модулей, сессия и хранилище
  e2e/            # браузерные сценарии
```

- `domain` не импортирует другие слои, UI-фреймворк, игровой движок, DOM, браузерное хранилище или сетевые API.
- `use-cases` зависит от `domain`; доступ к внешним системам получает через небольшие интерфейсы в `use-cases/ports`.
- Входные `adapters/input` и `adapters/runtime` вызывают `use-cases`. Выходные `adapters/persistence` и `adapters/content` реализуют порты. Сценарии не импортируют конкретные адаптеры.
- `presentation` вызывает команды приложения и читает снимки состояния. Не изменяет мир напрямую и не вычисляет нарушения. Публичные снимки имеют вложенные readonly-типы и защищены от записи во время выполнения; React получает показатели поездки, Phaser — снимок мира.
- `bootstrap` связывает слои. Только здесь выбираются конкретные адаптеры и создаются общие экземпляры сервисов; при завершении освобождаются обработчики, подписки и экземпляр Phaser.
- Phaser отображает результат доменной симуляции и не ведёт независимую физику машины. React получает показатели и события, а не весь изменяемый мир на каждом кадре.
- `use-cases` обновляет состояние разбора, а React показывает его; сценарий не вызывает React-модалку напрямую.
- `LearningContentProvider` возвращает кандидатов. Правила соответствия, приоритет выбора и оценка ответа находятся в `domain/learning`.
- Будущий HTTP-поставщик подключается через существующий порт в `bootstrap`. Бэкенд, HTTP-клиент и серверные контракты сейчас не создавай.
- Обратные и циклические зависимости запрещены. Не импортируй конкретное хранилище или компонент из доменной логики.
- Карта и учебные материалы — данные с валидацией при загрузке, а не условия, разбросанные по UI. Не зашивай ID конкретного перекрёстка в общий детектор.
- Разделяй модули по ответственности. Не создавай абстракции для гипотетических будущих функций и каталог `utils` для несвязанных правил.

## Симуляция и нарушения

- Симуляция обновляется с фиксированным шагом времени и не зависит от FPS отрисовки. После паузы не проигрывай накопившееся реальное время.
- Исходный ориентир — 60 шагов в секунду с ограничением догоняющих расчётов. Окончательные параметры определяются измерениями, а не считаются уже проверенными.
- Время, ввод и случайность передаются явно. Одинаковое начальное состояние, шаги, команды и seed должны давать одинаковый результат.
- Пауза едина для машины, пешеходов, светофоров и доменных таймеров. Открытие карточки и потеря фокуса останавливают весь мир; при потере фокуса сбрасывай зажатые клавиши.
- Используй единые координаты мира и явные единицы: метры, секунды, м/с; перевод в пиксели и км/ч выполняй на границах отображения. Документируй направление осей и единицу углов.
- Каждый детектор получает предыдущее и текущее состояние и контекст дороги. Пересечения линий проверяй по движению между состояниями, чтобы не пропустить их на высокой скорости.
- Учитывай размеры машины, полосу, направление и связанный дорожный объект. При пересечении линии и смене сигнала в одном шаге нужен сигнал в момент пересечения и определённый порядок событий.
- Телепортация, возврат на дорогу и восстановление контрольного состояния не считаются движением через промежуточные линии. Задний ход и новый подъезд проверяются в контексте направления и эпизода.
- Детектор возвращает структурированную причину, факты и идентификатор эпизода. Он не открывает окно, не пишет историю и не выбирает вопрос.
- Повтор одного непрерывного эпизода не создаёт новые события каждый кадр. Условие завершения и повторного взведения детектора должно быть явным и проверяемым.
- Причины одного действия объединяются на уровне приложения в одну карточку; не создавай несколько конкурирующих модальных окон.
- Подбирай вопрос отдельным модулем по проверенным связям и обстоятельствам. Случайный вопрос по общей теме не считается точным соответствием ситуации.
- Для пешехода проверяй преимущество, намерение движения и причину изменения скорости или направления; близость к машине сама по себе недостаточна.
- Не запускай все проверки для всей карты на каждом шаге: выбирай релевантные объекты и нормы по расположению, связям и событиям. Выход объекта за экран не останавливает его логику.
- Не вводи выдуманные требования закона: обязательные секунды STOP, разрешённое превышение скорости, универсальное нарушение на жёлтый. Следуй ограничениям проверок из ТЗ.

## Состояние, история и повтор

- У мира один владелец состояния. UI получает снимок; не копируй изменяемое состояние машины в несколько независимых хранилищ.
- Владелец мира — игровая сессия в `use-cases`; структуры и правила изменения определяет `domain`. Постоянная карта отделена от изменяемого мира, локальное состояние интерфейса остаётся в React.
- При нарушении сначала заверши проверки шага, объедини связанные причины, поставь мир на паузу и сбрось ввод. Затем добавь запись в память и запусти сохранение и подбор материала; пауза не ждёт IndexedDB.
- Не выполняй загрузку материалов и запись в хранилище внутри доменного шага. Повторное сохранение записи с тем же ID не должно порождать дубликаты.
- Явно моделируй состояния поездки и причины паузы. Закрытие карточки не должно снимать другую действующую причину паузы.
- Дорожное нарушение и попытка ответа — отдельные записи со стабильными ID. Правильный ответ не удаляет нарушение; неверный ответ не создаёт дорожное нарушение.
- Сохраняй самостоятельность ответа, просмотр подсказки, пропуск и повторную попытку. Новая попытка не переписывает предыдущую.
- Повтор восстанавливает полный контекст ситуации: мир, фазу светофора, пешеходов, состояние детекторов, время симуляции и случайность. История попыток при этом сохраняется.
- Если точное восстановление невозможно, обозначай действие как возврат в безопасное место, а не повтор той же ситуации.
- Храни ограниченный набор контрольных состояний. У повторной попытки свой ID; после повторного открытия приложения новая поездка начинается в безопасном месте.
- Игнорируй автоповтор клавиатуры при переключении поворотника.
- Доступ к браузерному хранилищу только через адаптер. Сохраняемые данные имеют версию схемы, проверку при чтении и явную обработку несовместимости.
- Ошибка чтения, повреждённые данные или переполнение хранилища не должны ломать текущую поездку. Сообщай о невозможности сохранения; не удаляй историю молча.

## Учебные данные

- Не придумывай официальные вопросы, номера билетов, правильные ответы и нормативные цитаты.
- Для материала храни стабильный ID, источник, редакцию или дату проверки, категорию, нормативные пункты и связи с причинами нарушений.
- Отделяй исходный вопрос и нормативную цитату от авторского объяснения. Разные редакции не смешивай без явного обозначения.
- Непроверенные заглушки помечай как демонстрационные; они не должны попадать в выпуск как официальные материалы.
- Проверяй ссылки между правилами и вопросами, уникальность ID, наличие правильного варианта и ресурсов. Для каждой выпускаемой причины нарушения нужны проверенные объяснение и нормативное основание. Вопрос не обязателен; проверяй его данные и связи только если он включён как дополнительный материал.
- Результат ответа определяется исходным вопросом, факт нарушения — симуляцией. Не связывай эти решения общим флагом успеха.
- История сохраняет версии карты, правил и использованных материалов. Если вопрос не найден, покажи доступное объяснение и разреши продолжение; отсутствие вопроса не блокирует выпуск по ТЗ 0.2.0-preview.1. Отсутствие проверенного объяснения или применимого нормативного основания остаётся препятствием к выпуску соответствующей причины.

## Решения, которые ещё нужно уточнить при реализации

- Геометрия машины, параметры управления, начало и завершение манёвров.
- Технические допуски остановки и пересечения; они не являются нормами ПДД.
- Порядок совпавших событий, границы эпизодов и объединение причин.
- Момент контрольного состояния для повтора, проверенная подборка материалов, целевые устройства и показатели производительности.
- Сохраняй вертикальный цикл каждого правила: движение → проверка → карточка → история → повтор. Фактические решения и ограничения — в docs/IMPLEMENTATION.md; проверенные материалы — в docs/implementation/CONTENT.md; незавершённая приёмка — в docs/implementation/0.3.0/ACCEPTANCE.md.

## Проверки и порядок работы

- Все тесты храни в `tests/`, разделяя по видам: `unit`, `integration`, `e2e`. В `src/` тестовых файлов быть не должно. Модульные и интеграционные тесты называй `*.test.ts`, браузерные — `*.spec.ts`.
- Перед изменением кода и интерфейса прочитай `docs/STYLEGUIDE.md`; запуск и команды качества находятся в `README.md`.
- Единая проверка — `npm run check` (типы, ESLint, Stylelint, Prettier, тесты). Автоисправления — `npm run fix`; после них проверь diff. Предупреждения линтеров недопустимы.
- Используй семантические CSS-переменные, единые состояния элементов и видимый клавиатурный фокус. Не отключай правила ради прохождения проверки без конкретного обоснования.
- После правок исходников выполняй `npm run build`; при изменении интерфейса или игрового цикла также `npm run test:e2e`. GitHub Actions повторяет проверки после push/PR; локальный успех не равен зелёному CI.
- Перед правками проверяй `git status`, сохраняй чужие и несвязанные изменения. Меняй только то, что нужно для задачи.
- Для игровой логики нужны детерминированные unit-тесты: нарушение, правильное действие, граница условия, повтор эпизода и повторный проезд.
- Проверяй отдельно разрешённый въезд на зелёный, STOP до/после линии, момент включения поворотника, непрерывное превышение и реальное влияние на пешехода.
- Интеграционными тестами покрывай общую паузу, потерю фокуса, сохранение истории, сбой хранилища и повтор ситуации.
- E2E проверяют основной цикл из ТЗ, продолжение без ответа и журнал. Не заменяй проверки поведения одними скриншотами.
- При настройке проекта закрепи границы импортов в ESLint. Проверяй `use-cases` с адаптерами в памяти, IndexedDB и загрузку материалов — интеграционно. Производительность оценивай замерами симуляции, отрисовки и памяти.
- Для изменения только документации достаточно проверить ссылки, согласованность текста и `git diff --check`; не устанавливай зависимости ради такой проверки.
- После появления проекта выполняй относящиеся к правке команды проверки из README и реально существующих scripts. Не сообщай об успешных тестах, которые не запускались.
- При изменении архитектуры обновляй этот файл и README в той же задаче. Существенный выбор документируй кратко: решение, причина, последствия.
- Не создавай коммиты, не отправляй изменения на remote и не публикуй игру без запроса пользователя.
- В результате кратко сообщай, что изменено, что проверено и какие ограничения остались.
