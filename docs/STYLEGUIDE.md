# Стайлгайд проекта

Правила написания кода «Тихого города». Компоновка, визуальное поведение и параметры оформления описаны в [DESIGN.md](DESIGN.md), архитектурные границы — в [AGENTS.md](../AGENTS.md), запуск — в [README.md](../README.md).

## Инструменты и команды

| Инструмент                  | За что отвечает                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------ |
| TypeScript strict           | Типы, неиспользуемые переменные и параметры                                                            |
| ESLint с проверкой типов    | Ошибки TypeScript, потерянные Promise, небезопасный `any`, неправильный контекст `this`, границы слоёв |
| React Hooks + React Refresh | Правила хуков, зависимости эффектов и совместимые с HMR экспорты компонентов                           |
| jsx-a11y                    | Подписи элементов, ссылки, ARIA и базовая доступность JSX                                              |
| Stylelint + stylelint-order | Корректность CSS, дубли, имена классов и порядок свойств                                               |
| Prettier                    | Формат TS, TSX, JS, CSS, JSON, Markdown и YAML                                                         |
| EditorConfig                | UTF-8, LF, отступы и финальный перевод строки                                                          |

`npm run check` запускает типы, оба линтера, проверку форматирования и тесты логики. Предупреждения линтеров завершают проверку ошибкой.

`npm run fix` применяет доступные автоисправления ESLint и Stylelint, затем Prettier. Не все ошибки исправимы автоматически: если команда остановилась, исправь оставшиеся ошибки по сообщениям и запусти её снова. Всегда просматривай diff после автоисправления.

## TypeScript и React

- Два пробела, одинарные кавычки, точка с запятой, завершающие запятые; ширина строки 100 символов. Формат задаёт Prettier, ручное выравнивание пробелами не нужно.
- Компоненты — `PascalCase.tsx`, остальные модули — `kebab-case.ts`. Переменные и функции — `camelCase`, типы — `PascalCase`, настоящие глобальные константы — `UPPER_SNAKE_CASE`.
- Импорт типов помечай `type`. Внешние непроверенные данные принимай как `unknown` и проверяй на границе адаптера. Не маскируй проблему с помощью `any` или цепочек приведения типов.
- Условия и циклы всегда со скобками `{}`. Используй строгое сравнение `===` / `!==`.
- Promise нужно `await`-ить, вернуть или явно обработать. `void` допустим для намеренно фонового вызова только когда ошибка обрабатывается внутри вызываемой операции или через `.catch()`.
- Callback-пропсы записывай как функции: `onClose: () => void`. Не передавай несвязанный метод, использующий `this`.
- Хуки вызываются только на верхнем уровне компонентов и других хуков. Зависимости эффектов должны быть полными; освобождай подписки, обработчики и экземпляры движка.
- UI показывает состояние и вызывает сценарии. Не переноси проверки ПДД, сохранение и симуляцию в компоненты ради удобства.
- Выделяй компонент по самостоятельной ответственности: разбор, журнал, приборная панель. Не вводи универсальные обёртки, пока нет повторяющейся задачи.
- Не добавляй отключение правила на весь файл для одного нарушения. Локальное исключение должно содержать причину.

## CSS

Перед изменением интерфейса прочитай [правила дизайна](DESIGN.md). Там находятся палитра, токены, компоновка, поведение окон и матрица визуальной проверки. Этот раздел описывает способ написания CSS и не переопределяет дизайн.

- Повторяющиеся базовые цвета и радиусы используй через переменные. Специфичные цвета дорожных объектов и иллюстрации могут быть локальными; не меняй смысл красного STOP ради палитры.
- Имена CSS-классов — `kebab-case`: `.lesson-card`, `.answer-option`. Выбирай название по роли, а не по текущему цвету или порядку элемента.
- Сначала custom properties, затем обычные свойства по алфавиту. Stylelint расставляет их автоматически. Форматирование отступов и переносов оставь Prettier.
- Правила одного компонента держи рядом: основной вид, дочерние элементы, состояния. Адаптивные переопределения — в соответствующем media query.
- Не дублируй селектор в одном блоке. Не добавляй `!important` для борьбы с каскадом: сначала проверь порядок и специфичность. Исключения должны иметь объяснение.

## Доступность

- Для действия — `<button>`, для перехода — `<a href="…">`. Пустые ссылки `href="#"` не заменяют кнопки.
- Кнопкам только с иконкой нужен `aria-label`; декоративная графика не заменяет текстовую подпись.
- Диалог получает доступное название, удерживает фокус, закрывается с клавиатуры и возвращает фокус. Не убирай видимый фокус без равнозначной замены.
- `tabIndex={0}` у игрового поля с `role="application"` — осознанное исключение: поле принимает клавиатурное управление. Обычные карточки и текст не должны попадать в Tab-порядок.
- Проверка JSX линтером не доказывает полную доступность: клавиатуру, читаемость, контраст и поведение диалогов проверяй отдельно.

## Обоснованные исключения в настройках

- Prettier отключает конфликтующие правила оформления ESLint; семантические проверки остаются включёнными.
- `no-descending-specificity` в Stylelint отключён: единый CSS организован по отдельным компонентам, и одинаковые теги в разных ветках DOM дают ложные пересечения. Дубли селекторов остаются запрещены.
- `require-await` отключён только для тестов и локального поставщика материалов: они реализуют асинхронные порты без искусственных задержек. Потерянные и неправильно переданные Promise по-прежнему проверяются.
- Архитектурные запреты импортов снимаются в unit-тестах для интеграционных фикстур, но действуют в production-коде.
- Исходные ТЗ и архитектурный документ исключены из Prettier, чтобы автоформатирование кода не переписывало согласованные материалы. Новая документация форматируется.

## Перед завершением задачи

Для изменений только документации проверь форматирование, ссылки, согласованность с `DESIGN.md` и `git diff --check`. Для кода и интерфейса:

```sh
npm run fix
npm run check
npm run build
```

После изменения поведения интерфейса или игрового цикла также выполняй `npm run test:e2e`. Проверяй `git diff --check` и не включай чужие изменения в свою задачу.

GitHub Actions повторяет `check`, сборку и браузерные тесты на push и pull request. Наличие workflow не означает, что удалённый запуск уже прошёл.
